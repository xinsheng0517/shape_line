# 持续供料修复记录（2026-09-24）

## 问题定位

C1、C2、C5、C6 的四瓣挑战运行时在进入关卡时按 `def.stock` 为每个资源点预生成有限原坯。采集器取完初始缓存与储备后设置“该资源库存已耗尽”，不再出料。C1 每个资源点的旧总量仅为 8 个；观察到出口约 7 个后停机，可能是最后一个仍在采集器或传输链中。经典模式采集器本来按节拍持续生成，C4 的停止条件是独立的 60 秒关卡计时。

## 逻辑调整

四瓣挑战保留 C1/C5 每源 1 个、C2/C6 每源 2 个初始缓存，但取消资源总量上限。缓存为空且采集器空闲时，按资源点共享的递增序号生成新的完整原坯。多个采集器连接同一节点也不会产生重复物品 ID。出口堵塞时采集器保留当前物品，不继续生成；疏通后恢复。重置供料会清空本轮在途物品并重置初始缓存与序号。

无限出料曾使共享输送线持续被单一资源占满，四关原有测试产线无法完成合并。因此 V3 采集器改为每 3 个传送节拍产出 1 个原坯（当前为 6 tick），给不同来源在共享线路上留出汇流空档。经典关卡和 C4 的采集节拍不变。关卡按目标交付完成后停止模拟属于正常结算；传送线堵塞时仍会按背压等待。

界面蓝图库侧栏显示“持续供料 ∞”，并保留当前缓存、已发和废料计数；规则说明同步更新。

## 验证

- `test-infinite-supply.js` 对四关全部 3 个资源点分别连接采集器与回收装置：常规场景运行 1,000 tick，C1 一个资源点运行 10,000 tick，持续输出完整原坯且无库存耗尽状态。
- 同源双采集器、无下游堵塞后疏通、重置后再次长时出料均通过；所有生成单元 ID 唯一，当前缓存、在途、废弃与交付物料的单元数与生成数一致。
- C1/C2/C5/C6 的真实外部二级切割产线均可通关，参考线路分别在 694/890/780/1052 tick 达成目标，设备预算和原有星级线未变。
- 全部 16 个 `test*.js` 文件通过，修改的 JavaScript 语法检查通过，`node build.js` 成功生成 `dist/shape-line.html`。打包版浏览器检查确认侧栏显示无限供料且无脚本错误。

供料节拍变慢会拉长四瓣挑战的完成时间。后续若调整难度，可在保持无限供料与汇流公平的前提下优化线路调度，再根据试玩数据平衡节拍。
